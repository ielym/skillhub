# sched（任务调度器 v3）

## 核心定位

sched 是常驻单进程的**本地子任务调度器**，采用**生产者 / 执行分离**架构：

1. **常驻生产者**：每个启用任务常驻一个生产者进程，自行维护业务触发时间，发现动态任务后把「就绪 JSON」发布到 `outbox/`。生产者与执行进程分属不同管理范围，**永不因调度压力被暂停/限额/抢占**。
2. **调度器只控制执行进程运行规模**：看到有效就绪 JSON 即视为已就绪，不再判断业务执行时间、不设日历定时。
3. **动态运行目标**：没有写死的最大并发/排队上限/资源申请。调度器只观测执行进程的实测消耗与业务进展，平缓扩容（冷启动 1 个，逐步 +1），高优保护、累计退让。
4. **SQLite 执行库**：作业/attempt/事件/检查点/回执落盘，重启接管、进程身份核实、作业去重。
5. **统一执行协议**：心跳 + 进展 + 统一外部不足 + 检查点 + 协作暂停 + 幂等提交。断点恢复、协作暂停、可重放执行、幂等提交是**所有子任务的必需能力**。

**路径约定（全文统一）**：

- **代码根**：scheduler 仓库 clone 目录（`tasks/`、`runtime/`、`config.json` 的父目录；默认 `sched` 包上一级，环境变量 `SCHED_HOME` 覆盖）。
- **skill 目录**：本 skill 的安装目录（模板/参考在 `assets/`、`references/` 下）。

## 核心理念

| 维度 | sched 的规则 |
| --- | --- |
| 触发模型 | **生产/执行分离**：生产者发现业务事件并发布就绪 JSON，执行进程独立受控 |
| 任务形态 | **有限任务与长期任务同一套请求协议**：都提供心跳 + 业务进展；有限任务完成后另提交完成记录 |
| 资源 | **不填写资源申请**：调度器只观测执行进程实测 CPU/内存/IO 与业务效果，学习接近饱和的位置 |
| 外部资源 | **本地不记录**：不建接口/账号/隧道/配额/资源指纹关联图；外部不足统一用 exit 75 表达 |
| 新执行 | **生产者发布新作业 = 新 job_id**（由任务标识 + 稳定事件标识 + 业务版本确定，重放得到同一 job_id） |
| 进程协调 | **生产者自己管理**：多次新作业 = 生产者多次发布；禁止自然语言驱动 |
| 失败处理 | **退出码**：0 成功（需完成记录）、75 统一外部不足、其他非 0 业务/未知失败 |
| 断点/幂等 | **必需契约**：周期提交检查点、协作暂停、幂等提交（稳定幂等键 + 可核实提交记录） |
| 生命周期 | **只走协议**：事件通道（心跳/进展/不足）+ 控制通道（暂停命令）+ 检查点 + 退出码 |

## 适用 / 不适用

- **适用**：在代码根上创建新的被守护子任务；为已有子任务改配置/排障/交付验收；判断一个子任务能否/如何纳入守护；咨询 task.json、就绪 JSON、生产者/执行者、事件协议、退出码。
- **不适用**：调度器核心源码（`sched/` 包）本身的重构开发（走需求审查流程，不属于子任务创建）。
- **铁律：子任务作者只在 `tasks/<id>/` 自己的目录内工作，禁止改 `sched/` 包源码、禁止手改 `runtime/` 内文件。**

## 命令速查

均在代码根执行；确切行为与失败情形见 [configuration.md](references/configuration.md)。

```bash
sched serve                 # 常驻调度循环（前台）
sched status                # 全局状态（生产者 / 动态目标 / 存活 attempt / 队列 / 退让）
sched list                  # 已加载任务（task.json）
sched task validate <id>    # 校验任务清单（task.json + 入口存在）
sched task enable <id>      # 启用任务（写 task.json enabled=true）
sched task disable <id>     # 禁用任务
sched job list [task]       # 作业清单
sched job show <job_id>     # 作业详情 + attempts
sched job cancel <job_id>   # 显式取消（serve 在线走命令通道，离线直连撤进程树）
sched job requeue <job_id>  # 显式重排：关闭在途 attempt 并重新排队（运行中拒绝）
sched attempt list [job]    # attempt 清单
sched attempt cancel <id>   # 显式取消单个 attempt
```

## 铁律索引（H1–H14，违反任一条不得交付）

1. **H1 唯一执行通道**：正式执行只能由调度器扫描 outbox 就绪 JSON 触发；禁止 cron/手工跑/自触发执行进程。
2. **H2 生产/执行分离**：生产者进程与执行进程分属不同管理范围；禁止把执行资源控制/暂停命令施加到生产者。
3. **H3 生产者解耦可用性**：生产者把发现工作与调度器可用性解耦，调度器停止接收/数据库暂不可写时仍持久化并继续发布。
4. **H4 稳定作业标识**：作业标识由（任务标识 + 稳定事件标识 + 业务版本）确定，重放得到相同 job_id；禁止每次随机生成。
5. **H5 无丢失发布**：先持久化游标 + 待发布记录，再原子发布正式 JSON；成功后才标记已发布。
6. **H6 生命周期只走协议**：事件通道（心跳/进展/不足）+ 控制通道（暂停）+ 检查点 + 退出码；禁止自行删改 outbox/runtime 文件。
7. **H7 必走 SDK 契约**：执行者继承 `ExecutorTask`、生产者用 `Producer`，禁裸脚本绕过心跳/断点/分类。
8. **H8 断点/幂等是必需品**：周期提交检查点；外部写入用稳定幂等键 + 可核实提交记录；不满足需修复协议后接入。
9. **H9 本地不记录外部资源**：不把接口/账号/凭证写入调度元数据；统一不足只报状态，不报资源指纹/原始异常。
10. **H10 源码不动、数据不手改**：仅调试清理时按流程编辑数据文件。
11. **H11 子任务自包含**：每个 `tasks/<id>/` 独享完整代码，禁止 `tasks/shared/` 或共享业务逻辑（SDK `sched_task_sdk` 除外）。
12. **H12 运行参数写在配置里**：进程跑什么（date/topic/query 等）必须写在就绪 JSON 引用的配置文件里，禁止用 job_id 文件名反推。
13. **H13 及时打印进度日志**：及时写 stdout/stderr（`flush=True`）并同步发进展事件，禁止静默长跑。
14. **H14 协作暂停而非强杀**：执行者收到暂停命令后停止新工作、在安全边界提交检查点再退出；不依赖 SIGSTOP。

全文（含每条的细节与原因）见 [rules.md](references/rules.md)。

## 标准流程一句话

**阶段 0 设计**（定 id/优先级/生产者发现逻辑/执行者断点与进展/幂等键，选模板）→ **阶段 1 本地裸进程调试**（`_dev` 目录跑 producer/executor、断点与暂停演练）→ **阶段 2 放入 `tasks/<id>/`，调度器自动守护生产者并把就绪 JSON 转为执行进程**（`sched status`/`job show` 看原因）→ **阶段 3 跑通完整发布→执行→完成 + 暂停恢复演练** → **阶段 4 只认调度触发成功的交付验收**。
